### Form

- upgrade the final-form ecosystem to the versions that support React 19: `final-form@^5.0.1`, `final-form-arrays@^4.0.1`, `react-final-form@^7.0.1`, `react-final-form-arrays@^5.0.0` and `react-final-form-listeners@^3.0.1`. The type churn is upstream's Flow-to-TypeScript rewrite; the runtime differences this package absorbs or documents are listed below: the checkbox `checked` derivation and the mount reseed, both new in `react-final-form@7.0.1`, and the synchronous `FieldArray` mutators, the narrowed `FieldArray` default subscription and the two renders on mount, which `7.0.0` already had
- both `FieldArray` and `useFieldArray` are now Picasso's own typed wrappers over `react-final-form-arrays` (same props, same behavior): `<FieldArray>` stays a valid JSX element on `@types/react` 17 and 18 — upstream 5 declares its component as returning `ReactNode`, which only `@types/react` 19 accepts from a component — `useFieldArray<Item>()`, `FieldArrayRenderProps<Item>` and `FieldArrayProps<Item>` keep their item type parameter (the second, element type parameter of `react-final-form-arrays@3` was never used and is gone), and `fields.update(index, value)` is typed again: it always existed at runtime, upstream 5's declaration left it out. `FieldArrayMetaState` and `UseFieldArrayConfig` are exported alongside. The wrappers also keep subscribing the array field to every state key: `react-final-form-arrays@5` narrowed its default subscription to `length`, `value` and `error`, which leaves `meta.dirty`, `meta.touched`, `meta.submitting`, … `undefined` after mount — pass `subscription` to opt into the narrower one. Upstream narrowed it after nested arrays re-rendered on every field change (react-final-form-arrays#119), so a long or deeply nested array pays for the compatibility default; a follow-up moves the consumers that read the extra meta to explicit subscriptions and switches the default to upstream's in the next major
- **consumer action (types)**: `FormProps` no longer carries react-final-form 6's `[otherProp: string]: any` index signature, so extra props passed through `<Form>` or a wrapper typed `FormProps & …` now error — declare the props the wrapper accepts (they still reach the render props at runtime); `FormRenderProps['initialValues']` is `Partial<FormValues> | undefined`, and the `FormState` and `FieldMetaState` booleans (`dirty`, `submitting`, `touched`, …) are optional, matching what final-form fills for a subscription — read them as `initialValues ?? {}` and `Boolean(meta.touched)`; a `@ts-expect-error` on a `FieldArray` render prop that used to mis-type now reports as unused
- **consumer action**: `react-final-form` is a regular dependency of this package and its React context is instance-bound, so apps that also depend on `react-final-form` directly must move to `react-final-form@^7` / `final-form@^5` in the same upgrade. Staying on `^6` yields two library instances, and `useForm`/`useField` used inside a Picasso `<Form>` then throws `"... must be used inside of a <Form> component"`
- `react-final-form@7.0.1` derives a checkbox's `checked` from `parse(value)` where 6 and 7.0.0 used `format(value)`, an intentional upstream change (final-form/react-final-form#1074). `parse` is the DOM-to-state direction, so the documented pair — `format={value => value === 'true'}` with `parse={checked => (checked ? 'true' : 'false')}` — read a stored `'false'` through `parse`, got the truthy `'true'` back and rendered an unchecked box as checked; clicking it then submitted the wrong value, with nothing visibly wrong. `Form.Checkbox`, `Form.ButtonCheckbox` and `Form.Switch` keep the 6.x meaning for a checkbox that has no `value` of its own and passes a custom `format`: a deliberate divergence, kept until upstream settles the string-boolean case. A checkbox that carries a `value` belongs to a group, where `checked` is array membership, and `Form.Radio` compares `parse(value)` to the radio's `value`: both keep upstream's semantics, so a `format`/`parse` pair on those still needs re-verifying
- hidden checkbox inputs now render `value=""`, so consumer snapshots covering `Form.Checkbox` need a one-time regeneration
- fields register in an effect under `react-final-form@7` and render twice on mount (previously once) — visually inert, but render-count assertions in consumer tests will shift
- a field rendered without a `name` fails while mounting under `react-final-form@7`: it reads the field's initial value with `getIn(initialValues, name)`, gets the whole `initialValues` object back and calls `form.change(undefined, …)`, which throws `"Cannot call setIn() with undefined key"` whenever the form has `initialValues` or the field an `initialValue` (`react-final-form@6` tolerated the missing name until the first change). Development builds now throw a descriptive `[picasso]` error at the field instead; test fixtures that wrap a field must forward `name`
- the `FieldArray` mutators (`fields.push`, `fields.remove`, …) notify the form synchronously — a handler that runs during render (a mocked child calling `remove` while rendering, for example) now triggers React's "Cannot update a component while rendering a different component" warning; call the mutators from event handlers and effects
- `react-final-form-listeners@3.0.1` ships a broken `types` path, corrected by a pnpm patch for this repository's build; the four components are declared by this package (see the `useFormState` entry), so consumers are unaffected
- drop the `@types/react-final-form-listeners` dev dependency — the package now ships its own types
- **consumer note**: `FieldArray as jest.Mock` no longer compiles now that `FieldArray` is a declared component rather than a re-export — use `as unknown as jest.Mock`
