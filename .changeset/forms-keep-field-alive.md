### Form

- a field that unmounts and remounts, or that mounts over a value the consumer already wrote with `form.change()`, now keeps that value. `react-final-form@7.0.1` reseeds a field from `initialValues` whenever it mounts and final-form holds no field state for it, and final-form drops that state as soon as the field's last subscriber unregisters — which happens on any ordinary unmount, not only under `destroyOnUnregister`. A conditional field, a wizard step or an edit/preview toggle therefore came back holding the initial value rather than the edited one, and a field seeded with `''` was refilled, so its `required` validation never fired
- the form's values were right the whole time; only final-form's per-field state was missing. So that state is recreated from those values for exactly as long as react-final-form's mount effect needs to see it: a subscriber with no subscription and no validator is registered in the layout phase and released in the next passive effect. Nothing outlives the field: `getRegisteredFields()`, field errors and submit behaviour are what final-form reports without the workaround
- this covers every Picasso form field, including the radios of a `Form.RadioGroup` and the checkboxes of a `Form.CheckboxGroup`, which render react-final-form's `Field` rather than Picasso's: the group above them holds the claim, and it runs in the layout phase so that it precedes their mount effects. A react-final-form `Field` or `useField` a consumer renders directly inside a Picasso `Form` is not covered
- the claim carries the field's `beforeSubmit`, `afterSubmit`, `data` and `validateFields`, because it is the call that creates final-form's field entry and final-form applies those four only then: for an entry that already exists it re-applies `isEqual`, the validators, `initialValue` and `defaultValue`, but never the submit hooks. Without them react-final-form's own registration added nothing, and its `beforeSubmit` — the wrapper that applies `format()` to a `formatOnBlur` field at submit time — was dropped, so such a field submitted its raw value (`'5.0'` where the form displayed `'5.00'`) and a consumer `afterSubmit` never ran. In a `Form.RadioGroup` or `Form.CheckboxGroup` the group's own hooks now own the entry, where stock react-final-form gave it to whichever child registered first
- forms that set `destroyOnUnregister` are untouched: they ask for values to be dropped on unmount, which is the behaviour this works around
- this is a workaround for [react-final-form#1095](https://github.com/final-form/react-final-form/issues/1095); a fix is proposed in the still-open [#1096](https://github.com/final-form/react-final-form/pull/1096). It lives in one module, `Field/use-claimed-field-state.ts`, and is to be deleted once a `react-final-form` release contains a fix
